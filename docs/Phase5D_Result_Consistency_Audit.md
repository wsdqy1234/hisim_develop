# Phase 5D 结果一致性审计（Phase5D_Result_Consistency_Audit）

> 日期：2026-11-05 · 依据：`docs/p5d_results/` 原始数据（24 组 E2E JSON、P4-B trace CSV）、sglang 0.5.19 源码核查、复现实验
> 结论分三档：✅ 可信事实 · ⚠️ 仅特定配置成立 · ❌ 撤回/修正

---

## 核查 1：等容量 A/B 命中率一致性

**原始宣称**（5D 报告 §6）："等容量下命中率相同（容量驱动）"。

| 配置（总 Host 字节严格相同） | A 命中率 | B 命中率 | 差异 |
|---|---|---|---|
| α=0.5（Host=½WS, S2000） | 33.3% | 33.3% | 0 ✓ |
| α=1.0（Host=WS, S2000） | 66.7% | **63.3%** | **−3.4pp** |
| α=2.0（Host=2WS, S2000） | 66.7% | 66.7% | 0 ✓ |
| α=0.5/1.0（S8000） | 33.3/66.7% | 33.3/63.3% | 同上模式 |

**裁定**：
- ✅ α=0.5 与 α=2.0：A=B 成立（容量严格主导）。
- ⚠️ **α=1.0：B 低 3.4pp（RC 2200 vs 2000）**——trace 模拟器的重插入用全局交替计数器分配介质（不按对象原介质），复用阶段打乱 HBF/DRAM 配比、局部驱逐多淘汰 ~200 对象。这是**模拟器放置记账伪影**，不是 HBF 介质差异；V1b 对象感知重放置可消除（见 5D 报告 §9-4）。
- ❌ **修正宣称**："等容量替代下命中率相同"仅在 α=0.5/2.0 成立；α=1.0 时 B 存在 −3.4pp 的放置开销，须注明来源。

## 核查 2：Backup P95 "5.6×" 改善

**原始宣称**（5D §6 摘要行）："备份 P95 5.6×"（2.87ms → 0.51ms）。

复查 trace CSV（放置修复后重新生成）：

| 配置 | A backup P95 | B backup P95 |
|---|---|---|
| α=0.5 | 2.87ms | 2.87ms |
| α=1.0 | 2.87ms | 2.87ms |
| α=2.0 | 2.87ms | **2.87ms** |

**裁定**：
- ❌ **撤回**。0.51ms 出自**修复前的 sticky-HBF 放置版本**（HBF 先填满且驱逐路径不触发，备份几乎全落 HBF），且与 2.87ms 不同 α。修复后（V0 式 70/30 交替 + 每介质独立 LRU）任何等容量配置下 P95 均被 30% DRAM 备份（2.87ms）钉住。
- ✅ 可保留的修正表述：**backup p50（媒体 I/O 层面）0.487ms vs 2.87ms（5.9×）**——70% 走 HBF 条带写；P95 无改善（DRAM 份额决定尾延迟）。若要 P95 改善需全 HBF 放置（容量 α≥2 且放置策略偏好 HBF），属放置策略问题而非介质问题。

## 核查 3："Restore p50 143×" 的口径

**原始宣称**："恢复 p50 143×"（2.87ms → 0.02ms）。

**裁定**：
- ⚠️ **口径修正**。2.87/0.02ms 是 **trace 模型中的恢复 I/O 服务时间**（38.99MB：DRAM 13.6GB/s vs HBF 8×200GB/s 条带），作为 TTFT 代理直接写入 trace 的 ttft_p50 字段。它**不是端到端 TTFT**。
- ✅ 端到端口径（E2E 实测，n2）：reuse TTFT **7.40ms → 4.50ms（−39%）**——DRAM 路径 2.87ms 与批内另一请求的 DRAM 加载并行后仍为瓶颈（槽位耦合，5C 结论在对象化路径下不变）。
- 今后所有"143×"表述须标注"恢复 I/O 服务时间（trace 模型，非 E2E TTFT）"并与 E2E 数字并列。

## 核查 4：n2 TTFT 16.8→5.4ms 的请求级分解

E2E 实测（`p5d_runs/n2_{A,str}.json` + BATCH-TIME 行）：

| 项 | n2_A（纯 DRAM） | n2_str（HBF 条带） |
|---|---|---|
| reuse 请求 TTFT（各 2 个） | **7.40ms** | **4.50ms** |
| ├ Host Load 批时长 | 5743μs（2×DRAM 2.87ms **串行**） | 2871μs（DRAM 2.87 ∥ HBF 0.024ms） |
| ├ Prefill infer（1tk 重算） | 1.63ms | 1.63ms |
| ├ Backup | 0（reuse 批无备份） | 0 |
| ├ L3 / Recompute | 0 / 1tk | 0 / 1tk |
| └ 调度/基础开销 | ~0.03ms | ~0.03ms |
| p95（6 请求含首请求冷启动） | 16.8ms | 5.4ms |
| p50 | 7.97ms | 4.23ms |

**裁定**：
- ✅ 改善机制明确：**一个 reuse 的加载从 DRAM 移到 HBF 后与另一 DRAM 加载并行，批加载 5.74→2.87ms**；TTFT 7.40→4.50（−39%）。
- ⚠️ **p95=16.8ms 含首请求冷启动伪影**（A 首请求 16.80 vs str 首请求 3.10，均为 build 非复用），"16.8→5.4" 混入了与 HBF 无关的冷启动差。诚实口径：**reuse 级 7.40→4.50ms（−39%）、p50 7.97→4.23ms（−47%）**。

## 核查 5：R/W 分离策略的迁移成本

**原始呈现**（5D §3 表 rw-separated 行：restore 0.19ms + backup P95 3.90ms"双赢"）。

**裁定**：
- ⚠️ **标注为理想放置对照**。`migrate_object` 仅移动注册表记账（win_bytes/extents/计数），**未计算迁移的真实读写流量、容量与等待成本**（源码 docstring 已声明"data movement timing is the caller's responsibility"，报告未向读者声明）。
- 正确解读：该行证明"**若**读对象已位于专用 WIN（静态分离放置）**则**双赢"——即放置级分离的收益上界。真实迁移成本（每字节一次读+一次写，占用 2× 介质带宽）未建模，列为 5E.2 待办。

## 核查 6：G4 时间门语义（restore 早于 backup 完成）

**原始实现**：not-ready → 返回 0 字节、0 时长的 stats；而调用方（HOST-LOAD）已按树匹配把 tokens 计为 HBF 命中 → **潜在虚假快速恢复**（0 时长加载 + 命中计数）。

**裁定**：
- ⚠️ **确认存在（潜在）缺陷，已修复**。E2E 24 组 run 中 `n_stale_blocked_restores=0`（barrier 写模式下时钟总是先越过 backup 完成），**未影响任何已发布数字**——但若触发即产生假快恢复。
- ✅ 修复（本阶段）：改为 **wait-then-read**——等待至最早 ready_time 再读取，等待计入 total 与 queue_wait，media_time 单独上报（同时满足核查 3 的口径分离）。单元测试 `test_g4` 已更新（restore@1ms → total≈3.1ms = 等待 2.9 + 读 0.19，media_time 0.19ms）。
