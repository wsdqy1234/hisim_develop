## E1：效率本征实验（封闭负载，Layer A）

目的：在**受控 I/O 模式**下回答"8-WIN 池能否达到 80% Fixed Pool Efficiency"（=实际聚 合 BW / 8×额定）。

1. **读效率矩阵**：I/O 尺寸 {1, 2, 4, 8MB} × 延迟 {5, 7.5, 10μs} × QD {8, 16, 32, 64} × 访问 {seq, rand} × 接口 {无, 112s, 112pw, 896s, ≥1280}——输出 5C P2/P4 表的扩展版，标注每个 cell 的效率与瓶颈资源（media/interface/QD 槽位）
2. **写效率矩阵**：同上（写对接口不敏感，预期 80% 可达——5C 结论复验）
3. **读写混合**：读写比 {1:1, 3:1, 10:1} × 双工/半双工——R/W 分别统计（不合并分母），报告读效率、写效率、相互干扰（head-of-line 5C P5 已测 22×——对象化后复测）
4. **对象化放置效率**：object-balanced vs block-striped vs hotspot（负对照）在 340tk/4K/16K 对象尺寸下的池化效率——5D P1 表已给单对象 8× 写加速，本项补**多对象并发**时的每 WIN 队列分布（WIN 负载不均衡度 = Gini/最大最小比）

## E2：工作负载级收益（E2E，正确配比规则）

目的：把 E1 的本征效率映射到 QoS 收益（n2/n4/agent/churn × A/B70 配对）。

1. **配对比率表**（每行 A 基线 = 纯 DRAM 等总 Host 容量）：TTFT p50/p95、TPOT、吞吐、命中率、HBF/DRAM 有用字节、每 WIN 带宽/利用率/队列等待、Backup/Restore 完成时间——5E.1 §3.2 已出 n2/n4/4K/16K，补 **N=8/16**（需 batch 支持）与 **churn/混合负载**
2. **接口敏感性分区**：已知混合命中下接口 ≤3.5%（5E.1 §3.3）；补 **全 HBF 命中场景**（HBFO 放置 + 复用波并发 2/4/8）——预判 112 类接口成为 HBF 侧门限（16.8ms/16K 对象）但绝对值仍优于 DRAM；≥1280GB/s 接口时媒体条带成为门限（1.17ms）——**这是 80% 接口问题的 QoS 侧答案**
3. **R/W 分离真实成本**：把 migrate_object 升级为真实迁移（读旧 WIN + 写新 WIN，计费 2× 字节 + 等待），复测 5D P2 表——验证"分离双赢"在真实迁移下是否仍成立（预期：稳态成立，瞬态迁移成本与一次 backup 相当）
4. **V1b 价值感知放置对照**（独立开关 `HISIM_PLACEMENT=v1b`，V1a 默认不变）：修复 n4 命中 678<1017 与 agent churn 128/req——按对象 age/hit 预测分配 WIN 与池，对照 V1a 的配对比率

## E3：容量-收益终版（trace 模型 + 修正口径）

1. 重插入按**对象原介质**回放（消除 5D 审计 #1 的 −3.4pp 记账伪影），复跑 α ∈ {0.5, 1, 2} × WS ∈ {78GB…800GB} 等容量 A/B/C——终版命中率-容量曲线 + **p50/p95 backup & restore I/O 时间**（不用 P95 混口径）
2. 800GB 扩容场景：会话规模 20K-30K，报告容量收益（+10pp 量级复验）与介质收益（恢复 I/O p50）**分别归因**
3. 与 E2 QoS 数字联合出**收益瀑布**：容量（命中率）→ 放置（WIN 负载）→ 媒体/接口（I/O 时间）→ 批并行结构（TTFT）——每级单独归因，不再合并宣称

## E4：结论模板（预注册，防口径漂移）

- 80% 效率结论按资源分列：**media（池内）/ interface（封装）/ downstream（互连）/ QD 槽位**，各自给"80% 可达/不可达+数学上界"
- 收益结论三口径并列：**I/O 服务时间 / 批加载时长 / E2E TTFT p50-p95**（5D 审计 #3/#4 教训）

- 验收：E1-E3 全部 CSV+JSON 落盘、配对对照、守恒检查、120 项测试 + 新增项不回归
