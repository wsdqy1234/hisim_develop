**先修正了哪些会影响结论的问题**

1. **对象 WIN 路由与容量账本**：显式将条带目标 WIN 传给实际服务资源；对象容量由 registry 管理，恢复片段不重复分配容量，释放/覆盖/重用正确回收并保持版本历史。
2. **Trace 与统计**：保存精确提交/完成时刻、完整节点和对象版本、真实 WIN 子事件；请求量与完成量分开，缺失细分标 null；同时到达 burst 与按区间重建的在途 QD 分开。
3. **虚拟时钟因果**：修复新版 SGLang 局部 running batch 尚在运行时被误判为空闲的问题；时钟拒绝回退，负时延会触发验收失败。
4. **占位恢复重复计费**：`mock_lbk` 只保留诊断记录，不再改变 WIN/DRAM 游标、计数或权威恢复时长。
5. **L3→HBF 物化缺口**：原生页面读取实际接受的前缀才登记并写入 HBF；同时生成 generic/WIN 来源账本。ACK 表示元数据提交，后续读取仍需通过 program-ready 门禁。
6. **消费时刻与复现入口**：非 overlap 消费时刻移到 Host Load 完成后；每个案例独立目录和进程组，固定 token/到达时刻/配置哈希，避免生成式健康探针污染统计。

压力案例曾揭示两次 128-token 假命中：请求层报告命中，HBF registry 实际没有对象。本轮修复后，两笔 L3 来源写共 29,360,128B，与后续真实读取一一匹配，全部为 complete。链路示例为 SSD 预算完成 20.005s → HBF program 完成 20.0064336s → Host 读取 20.00927245s。未通过的开发案例保留在旧目录，不计入最终成果。

**实验条件与矩阵**

模型为本机 Qwen3-0.6B，28 层、8 KV heads、head_dim=128、BF16、TP=PP=1，KV 为 **114,688B/token（112KiB）**。逻辑 Prefix 为 340/4096/16384 tokens，另有 8 个独有 suffix tokens、16 个输出 tokens。逻辑需求分析排除 suffix/output。

每组普通负载先建立 4 个不同 Prefix，再对前 2 个做两轮复用；churn 负载在每轮复用前增加 4 个新对象。到达时间、token 内容及排序固定。全部场景开启相同 shared-DRAM 与 L3 barrier。平台/预测器沿用原配置，未调参追求性能。

WIN 输入为每 WIN 100GB、顺序读/随机读/写 200/100/10GB/s。读延迟取给定 5–10μs 范围的中点 7.5μs；写延迟 100μs 仍为假设。接口扫描值均为假设。800GB 是 WIN 物理供给模型的逻辑容量，以下 Host 配额是为实验而缩放的可用缓存容量。

| Case | Host 配额（GB） | 复用阶段 Prefix 命中率 | HBF 实际恢复（MB） | DRAM 实际恢复（MB） |
|---|---:|---:|---:|---:|
| short_mixed_v4 | 0.265159 | 100% | 38.994 | 38.994 |
| short_dram_v4 | 0.265159 | 100% | 0 | 77.988 |
| p4k_hbf_v4 | 2.849767 | 100% | 939.524 | 0 |
| p16k_hbf_v4 | 11.305484 | 100% | 3758.096 | 0 |
| short_churn_v4 | 0.172032 | 18.82% | 29.360 | 0 |
| short_churn_c3000_v4 | 0.344064 | 84.41% | 24.314 | 107.348 |
| short_churn_c6000_v4 | 0.688128 | 100% | 77.988 | 77.988 |
| short_mixed_str43_v4 | 0.265159 | 100% | 38.994 | 38.994 |

GB/MB 均为十进制。命中率为复用阶段的已复用 Prefix tokens / 请求 Prefix tokens，覆盖所有缓存层级，独有 suffix 不参与。L3 恢复可能随后经过 Host，因此 L3 consumed 不能与 Host 流量简单相加。

**成果一：容量需求与带宽需求必须联合观察**

三个 churn 容量点保持业务、L1=1024 tokens、放置策略、L3 和预测器不变，仅改变总 Host 容量：

| Host tokens | Host 容量（MB） | 复用 Prefix tokens | 命中率 | 实际 Host 恢复量（MB） |
|---|---:|---:|---:|---:|
| 1500 | 172.032 | 256 / 1360 | 18.82% | 29.360 |
| 3000 | 344.064 | 1148 / 1360 | 84.41% | 131.662 |
| 6000 | 688.128 | 1360 / 1360 | 100% | 155.976 |

容量增加后，更多 KV 得以复用，读取量随之增加、重算减少。需求画像必须同时报告命中与重算，否则会低估低容量配置下被重算替代的读取需求。本轮只测试三个点，不能称 688MB 为最小需求容量。

![实际 Host 容量敏感性](../../hbf_research_results/20261106_figures_v4/actual_host_capacity.png)

另有一套独立的全引用字节 LRU 参考曲线，包含缓存 miss，输出复用距离、复用间隔、唯一 Prefix 并集和达到重复引用目标命中率的采样容量。churn 的唯一 Prefix 并集约 467.927MB，离线 LRU 的采样 C95 为 350.945MB。它采用独立 LRU 假设，不能等同于带 HBM、分池与 L3 的实际 SGLang Host 策略。

**成果二：形成可复核的效率边界**

主指标固定为完成有效字节/观察窗口，再除以整池标定值 1600/800/80GB/s，纯顺序读、随机读、写分开报告。闭环扫描每点提交 512 笔请求，末尾全部 drain，窗口含起始填充和尾部完成。这里每个合成 I/O 针对单个 WIN；端到端一个条带对象可产生多个 WIN 子 I/O，二者 QD 不能混用。

| 顺序读条件（4MiB、QD16、均衡） | 交付带宽 | 固定整池效率 |
|---|---:|---:|
| 无接口限制假设 | 1600GB/s | 100% |
| 共享 112GB/s | 112GB/s | 7% |
| 共享 896GB/s | 896GB/s | 56% |
| 共享 1280GB/s | 1280GB/s | 80%，未严格超过 |
| 共享 1600GB/s | 1600GB/s | 100% |

严格 >0.8 的顺序读需要有效交付 >1280GB/s，接口还需留出其他损耗余量；随机读和写的对应值为 >640、>64GB/s。大 I/O、充分并发、均衡、无接口限制下的 100% 是输入包络与模型结果，未证明真实硬件效率。Layer A 没有经标定的 WIN 内部 QD 扩展模型。

**成果三：条带粒度是本轮已验证的改进因素**

在完全相同的 340-token Prefix 业务、容量及读写参数下，只改变条带大小：

| 条带大小 | 实际恢复覆盖 WIN | 38,993,920B 恢复时长 | 单次有效读带宽/1600GB/s |
|---|---:|---:|---:|
| 128 tokens | 3 | 73.40032μs | 33.20% |
| 43 tokens | 8 | 24.65792μs | 98.84% |

固定 Trace 搜索与完整端到端运行得到相同结果。恢复时长下降约 66.4%，数据量与命中集不变。这是模型内的**单次恢复效率**，不能当作持续饱和效率、硬件测量或 TTFT 改善率。

43 并非通用最优值。固定回放中 32-token 条带虽覆盖 8 个 WIN，字节不均衡仍使单次效率约为 66.4%；可见 WIN 数与字节均衡都需检查。全局默认策略未改，43-token 仅作为配对实验参数。

**成果四：需求与接口供给的条件匹配**

以“两并发 Prefix 均需从 Host 全量恢复、20ms 内完成”为例，条件有效读取需求为：

| Prefix | 单个 KV 量 | 两并发 20ms 所需有效带宽 |
|---|---:|---:|
| 340 tokens | 38.994MB | 3.899GB/s |
| 4096 tokens | 469.762MB | 46.976GB/s |
| 16384 tokens | 1879.048MB | 187.905GB/s |

20ms 是敏感性示例，并非用户已确定的生产 SLA。分析包还输出 1/10/100ms 曲线及明确容量基准的容宽比；容量可以选择完整 Prefix 并集、指定策略/命中率下的容量，不能互换。

16K 固定到达 Trace 的最大逻辑恢复时间如下。原配置无接口限制的回放误差为零，4 个选定 Trace 均成功复现原模型时间。

| 共享接口假设 | 最大恢复时间 |
|---|---:|
| 无约束 | 1.1744ms |
| 112GB/s | 29.7120ms |
| 896GB/s | 2.0972ms |
| 1280GB/s | 1.4680ms |
| 1600GB/s | 1.1744ms |

112GB/s 下的结果包含队列与其他 I/O 竞争，超过孤立单请求的约 16.8ms。供给匹配应检查并发、突发和队列。业务满足服务窗口与整池饱和效率 >0.8 分开报告。

**下一轮建议**

优先将条带大小、对象尺寸和 WIN 字节均衡形成一般化配置规则，并扩展共享 Prefix、到达强度和并发负载；围绕目标命中率/恢复时限细化容量区间。取得单 WIN 的 I/O Size×QD 曲线及 UB 接口资料后，再替换包络假设、评估硬件效率。现有数据已经可以支持这些研究，暂不需要以 TTFT 或 L3 Barrier 优化作为前置任务。
