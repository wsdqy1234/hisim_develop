# 第一部分：5D 结果一致性审计（P0）

> 日期：2026-11-05 · 依据：`docs/p5d_results/` 原始数据（24 组 E2E JSON、P4-B trace CSV）、sglang 0.5.19 源码核查、复现实验

### 核查 1：等容量 A/B 命中率一致性

**原始宣称**（5D 报告 §6）："等容量下命中率相同（容量驱动）"。

| 配置（总 Host 字节严格相同） | A 命中率 | B 命中率 | 差异 |
|---|---|---|---|
| α=0.5（Host=½WS, S2000） | 33.3% | 33.3% | 0 ✓ |
| α=1.0（Host=WS, S2000） | 66.7% | **63.3%** | **−3.4pp** |
| α=2.0（Host=2WS, S2000） | 66.7% | 66.7% | 0 ✓ |
| α=0.5/1.0（S8000） | 33.3/66.7% | 33.3/63.3% | 同上模式 |

**裁定**：
- ✅ α=0.5 与 α=2.0：A=B 成立（容量严格主导）。
- ⚠️ **α=1.0：B 低 3.4pp（RC 2200 vs 2000）**——trace 模拟器的重插入用全局交替计数器分配介质（不按对象原介质），复用阶段打乱 HBF/DRAM 配比、局部驱逐多淘汰 ~200 对象。这是**模拟器放置记账伪影**，不是 HBF 介质差异；V1b 对象感知重放置可消除（见 5D 报告 §9-4）。
- ❌ **修正宣称**："等容量替代下命中率相同"仅在 α=0.5/2.0 成立；α=1.0 时 B 存在 −3.4pp 的放置开销，须注明来源。

### 核查 2：Backup P95 "5.6×" 改善

**原始宣称**（5D §6 摘要行）："备份 P95 5.6×"（2.87ms → 0.51ms）。

复查 trace CSV（放置修复后重新生成）：

| 配置 | A backup P95 | B backup P95 |
|---|---|---|
| α=0.5 | 2.87ms | 2.87ms |
| α=1.0 | 2.87ms | 2.87ms |
| α=2.0 | 2.87ms | **2.87ms** |

**裁定**：
- ❌ **撤回**。0.51ms 出自**修复前的 sticky-HBF 放置版本**（HBF 先填满且驱逐路径不触发，备份几乎全落 HBF），且与 2.87ms 不同 α。修复后（V0 式 70/30 交替 + 每介质独立 LRU）任何等容量配置下 P95 均被 30% DRAM 备份（2.87ms）钉住。
- ✅ 可保留的修正表述：**backup p50（媒体 I/O 层面）0.487ms vs 2.87ms（5.9×）**——70% 走 HBF 条带写；P95 无改善（DRAM 份额决定尾延迟）。若要 P95 改善需全 HBF 放置（容量 α≥2 且放置策略偏好 HBF），属放置策略问题而非介质问题。

### 核查 3："Restore p50 143×" 的口径

**原始宣称**："恢复 p50 143×"（2.87ms → 0.02ms）。

**裁定**：
- ⚠️ **口径修正**。2.87/0.02ms 是 **trace 模型中的恢复 I/O 服务时间**（38.99MB：DRAM 13.6GB/s vs HBF 8×200GB/s 条带），作为 TTFT 代理直接写入 trace 的 ttft_p50 字段。它**不是端到端 TTFT**。
- ✅ 端到端口径（E2E 实测，n2）：reuse TTFT **7.40ms → 4.50ms（−39%）**——DRAM 路径 2.87ms 与批内另一请求的 DRAM 加载并行后仍为瓶颈（槽位耦合，5C 结论在对象化路径下不变）。
- 今后所有"143×"表述须标注"恢复 I/O 服务时间（trace 模型，非 E2E TTFT）"并与 E2E 数字并列。

### 核查 4：n2 TTFT 16.8→5.4ms 的请求级分解

E2E 实测（`p5d_runs/n2_{A,str}.json` + BATCH-TIME 行）：

| 项 | n2_A（纯 DRAM） | n2_str（HBF 条带） |
|---|---|---|
| reuse 请求 TTFT（各 2 个） | **7.40ms** | **4.50ms** |
| ├ Host Load 批时长 | 5743μs（2×DRAM 2.87ms **串行**） | 2871μs（DRAM 2.87 ∥ HBF 0.024ms） |
| ├ Prefill infer（1tk 重算） | 1.63ms | 1.63ms |
| ├ Backup | 0（reuse 批无备份） | 0 |
| ├ L3 / Recompute | 0 / 1tk | 0 / 1tk |
| └ 调度/基础开销 | ~0.03ms | ~0.03ms |
| p95（6 请求含首请求冷启动） | 16.8ms | 5.4ms |
| p50 | 7.97ms | 4.23ms |

**裁定**：
- ✅ 改善机制明确：**一个 reuse 的加载从 DRAM 移到 HBF 后与另一 DRAM 加载并行，批加载 5.74→2.87ms**；TTFT 7.40→4.50（−39%）。
- ⚠️ **p95=16.8ms 含首请求冷启动伪影**（A 首请求 16.80 vs str 首请求 3.10，均为 build 非复用），"16.8→5.4" 混入了与 HBF 无关的冷启动差。诚实口径：**reuse 级 7.40→4.50ms（−39%）、p50 7.97→4.23ms（−47%）**。

### 核查 5：R/W 分离策略的迁移成本

**原始呈现**（5D §3 表 rw-separated 行：restore 0.19ms + backup P95 3.90ms"双赢"）。

**裁定**：
- ⚠️ **标注为理想放置对照**。`migrate_object` 仅移动注册表记账（win_bytes/extents/计数），**未计算迁移的真实读写流量、容量与等待成本**（源码 docstring 已声明"data movement timing is the caller's responsibility"，报告未向读者声明）。
- 正确解读：该行证明"**若**读对象已位于专用 WIN（静态分离放置）**则**双赢"——即放置级分离的收益上界。真实迁移成本（每字节一次读+一次写，占用 2× 介质带宽）未建模，列为 5E.2 待办。

### 核查 6：G4 时间门语义（restore 早于 backup 完成）

**原始实现**：not-ready → 返回 0 字节、0 时长的 stats；而调用方（HOST-LOAD）已按树匹配把 tokens 计为 HBF 命中 → **潜在虚假快速恢复**（0 时长加载 + 命中计数）。

**裁定**：
- ⚠️ **确认存在（潜在）缺陷，已修复**。E2E 24 组 run 中 `n_stale_blocked_restores=0`（barrier 写模式下时钟总是先越过 backup 完成），**未影响任何已发布数字**——但若触发即产生假快恢复。
- ✅ 修复（本阶段）：改为 **wait-then-read**——等待至最早 ready_time 再读取，等待计入 total 与 queue_wait，media_time 单独上报（同时满足核查 3 的口径分离）。单元测试 `test_g4` 已更新（restore@1ms → total≈3.1ms = 等待 2.9 + 读 0.19，media_time 0.19ms）。

# 第二部分：大 Prefix 128-token 根因分析（P1）

> 日期：2026-11-05 · 方法：阶段级插桩（`HISIM_LPF_DEBUG=1`：树转储 + match 逐节点追踪）+ 最小复现 + 源码核查（sglang 0.5.19 unified_cache / cache_controller / sim_storage）
> 原始数据：`/tmp/p5e_probe_*.log`、`/tmp/p5e_p*.log`（14 组前缀扫描 + 对照）

---

### 1. 结论先行（A/B/C 判定）

**5D 现象定性：Case B 的容量亚型 + 环境伪影，而非缓存/介质/对象机制的缺陷。**

- **A（缓存只存了 128 tokens）？否**。树转储证明 4K 前缀作为单一节点完整备份：
  `N14 p=5 key_len=4089 host_len=4089 host=(13,4101) evicted=1 backuped=1`——backup op 全量（`4090tk→HBF (469.07MB)`、16K 同理 `16378tk→1878MB`）。
- **B（存了完整、但匹配/恢复只找到 128）？是，但机制是容量-驱逐-retraction 级联**：reuse 的**第一次 match 是完整的**（`host_hit=4089, N15(key=4089, host=4089)`），第二次 match 变 0——两次之间对象被摧毁（见 §3 级联链）。
- **C（存恢完整、消费只算 128）？否**。被消费的 128 tokens 是真实的部分命中（`pf_complete=128`、LoadBytes=14MB、守恒 `0+128+3962=4090/4090` 全对）——缓存语义诚实，无虚计。

**128 的来源**：sglang 存储层常量 `STORAGE_BATCH_SIZE = 128`（`mem_cache/hicache_storage.py:23`）——被驱逐对象经**异步线程**按 128 token/批写 L3；reuse 探测（`_storage_hit_query`）落在写入进行中，只找到已完成的**第一批** → 恰好 128。4K 与 16K 出现**完全相同的 128**（时序竞态不会两次恰好相等）证实了批粒度机制。

### 2. 证据链

#### 2.1 容量充足时全量恢复（决定性对照）

| 配置 | max_total | host | 复用命中 |
|---|---|---|---|
| 2 builds + 1 reuse，ratio 3.0，无 L3 | 4096 | 12288 | **4089/4090（469MB）全量** |
| 同上 + storage 后端 | 4096 | 12288 | **4089 全量** |
| 5D 原负载（3 builds + 2 reuses），ratio 2.0 | 4096 | 8192 | 128 + 0（复现 5D） |
| 5D 负载 + **正确配比**（max_total 8192） | 8192 | 16384 | **2×4095 全量（2×469MB）** |

#### 2.2 5D 失败的机制级联（插桩还原）

```
L1(4096)=1 个 4K 前缀；host(8192)=2 个 4K 对象（8186/8192，零余量）
├─ build1 驱逐 build0 → backup#1(4090→L2) ✓
├─ build2 驱逐 build1 → backup#2(4090→L2) ✓（L2=8186，满）
├─ R0/R1(t=50) 同时到达，各自 match 到 4089（完整！）
├─ 批次组建：2×4089+16 > 4096(剩余) → 调度器先驱逐 build2 → backup#3
│    └─ host 余量 6 → 驱逐 LIVE L2 对象（LRU）→ 对象写入 L3（异步 128/批）
├─ 另一 reuse 的对象被驱逐 → 其 match 变 0 → 探测 L3 → 命中第一批=128
└─ 在途 host-load 的请求被 retraction → retraction_discard 释放其 host backup
     → 该请求第二次 match=0 → 全量重算（58.6ms）
```

关键代码（sglang 原生，零修改）：
- `unified_radix_cache.retraction_discard()`：retraction 释放 host_indices（被中止请求的加载作废——正确语义）
- `full_component.drive_host_eviction()`：host LRU 驱逐
- `cache_controller._page_backup()`：按 `STORAGE_BATCH_SIZE=128` 分批异步写
- `full_component.finalize_match_result_in_tree_core()`：host_hit = 逐节点完整 host_value 求和（无粒度截断）

### 5. 修复（P2：最小干预，SGLang 0 修改，V1a 不变）

1. **Prefix Capacity Rule（配置规则 + 运行时守卫）**：
   - `max_total_tokens ≥ n_concurrent_reuse × prefix + margin`（否则 retraction 摧毁在途 host 加载）
   - `host ≥ (live_objects + reinsert_wave) × prefix`（否则复用波的自插入驱逐 LIVE 对象）
   - 实现：`[HBF-WARN] prefix-capacity rule` 一次性运行时告警（hook 层，backup 时检测对象 >50% host 池）+ 本文档规则
2. **G4 wait-then-read**（顺带修复 5E.0 审计 #6 的潜在假快恢复）
3. **不做的**（按用户约束）：不强制全前缀命中（部分 L3 命中 + 诚实重算是正确缓存语义）；不改 V1a/调度/驱逐算法（V1b 留待后续）；SGLang 零修改

### 6. 期望可复用范围（P2 验收项 2）

按实际 Prefix Cache 匹配规则（节点边界 + `page_size=1` + auto-truncate 边界）：
- prefix P（P ≤ max_total−8）：backup = P（单节点），restore = P−1（首 token 不命中，SGLang 匹配语义）± truncate 6
- 多对象并发驻留要求单池连续容量 ≥ 对象大小（TieredHostKVCache `available_size=MAX` 语义）
- 128 = L3 异步写批粒度（STORAGE_BATCH_SIZE），仅在对象被 L2 驱逐后作为部分命中出现——非错误

### 7. 对 5D 报告 §4 的修正

5D "大前缀限制（V1a 备份路径节点覆盖缺陷）"的表述**错误**：备份路径无缺陷；真因是实验配比（L1/host 零余量）触发的 retraction/驱逐级联。5D §4 表中 p4k/p16k 的 0.6%/0.2% 命中是配比结果，非机制结果；p3 修复后矩阵（§P3 报告）给出正确配比下的真实数字。

#### 3.3 接口带宽假设对 TTFT 的影响（P3 核心问题）

**问题**：4K/16K 完整恢复后，接口假设是否显著影响 TTFT？

| 场景 | 无接口约束 | 共享 112GB/s | 共享 896GB/s | 随机读边界 |
|---|---|---|---|---|
| p4k str p95 | 151.6ms | 155.5ms（+2.6%） | — | 151.9ms（≈0） |
| p16k str p95 | 450.1ms | **465.7ms（+3.5%）** | 451.0ms（≈0） | 451.3ms（≈0） |

**答案：否——本工作负载形态下不显著（≤3.5%）**。机制：每轮复用波 = 1 个 HBF 加载（1.88GB：媒体条带 1.17ms / 112GB/s 接口 16.8ms / 随机媒体 2.34ms）与 1 个 **DRAM 共载加载（1.88GB/13.6GB/s = 137ms）并行**，批加载时长由 DRAM 侧主导，接口与访问模式的差异被并行结构吸收。896GB/s ≈ 无约束 ✓。
**边界推论（未在本矩阵触发）**：若放置使全部复用走 HBF（如 HBFO 对照），1.88GB@112GB/s=16.8ms 将成为 HBF 侧门限（媒体 14×），仍远低于所替代的 DRAM 137ms——接口假设仅在"全 HBF 命中 + 高并发复用波"下开始主导，列为 5E.2 实验项。

### E1：效率本征实验（封闭负载，Layer A）

目的：在**受控 I/O 模式**下回答"8-WIN 池能否达到 80% Fixed Pool Efficiency"（=实际聚 合 BW / 8×额定）。

1. **读效率矩阵**：I/O 尺寸 {1, 2, 4, 8MB} × 延迟 {5, 7.5, 10μs} × QD {8, 16, 32, 64} × 访问 {seq, rand} × 接口 {无, 112s, 112pw, 896s, ≥1280}——输出 5C P2/P4 表的扩展版，标注每个 cell 的效率与瓶颈资源（media/interface/QD 槽位）
2. **写效率矩阵**：同上（写对接口不敏感，预期 80% 可达——5C 结论复验）
3. **读写混合**：读写比 {1:1, 3:1, 10:1} × 双工/半双工——R/W 分别统计（不合并分母），报告读效率、写效率、相互干扰（head-of-line 5C P5 已测 22×——对象化后复测）
4. **对象化放置效率**：object-balanced vs block-striped vs hotspot（负对照）在 340tk/4K/16K 对象尺寸下的池化效率——5D P1 表已给单对象 8× 写加速，本项补**多对象并发**时的每 WIN 队列分布（WIN 负载不均衡度 = Gini/最大最小比）

### E2：工作负载级收益（E2E，正确配比规则）

目的：把 E1 的本征效率映射到 QoS 收益（n2/n4/agent/churn × A/B70 配对）。

1. **配对比率表**（每行 A 基线 = 纯 DRAM 等总 Host 容量）：TTFT p50/p95、TPOT、吞吐、命中率、HBF/DRAM 有用字节、每 WIN 带宽/利用率/队列等待、Backup/Restore 完成时间——5E.1 §3.2 已出 n2/n4/4K/16K，补 **N=8/16**（需 batch 支持）与 **churn/混合负载**
2. **接口敏感性分区**：已知混合命中下接口 ≤3.5%（5E.1 §3.3）；补 **全 HBF 命中场景**（HBFO 放置 + 复用波并发 2/4/8）——预判 112 类接口成为 HBF 侧门限（16.8ms/16K 对象）但绝对值仍优于 DRAM；≥1280GB/s 接口时媒体条带成为门限（1.17ms）——**这是 80% 接口问题的 QoS 侧答案**
3. **R/W 分离真实成本**：把 migrate_object 升级为真实迁移（读旧 WIN + 写新 WIN，计费 2× 字节 + 等待），复测 5D P2 表——验证"分离双赢"在真实迁移下是否仍成立（预期：稳态成立，瞬态迁移成本与一次 backup 相当）
